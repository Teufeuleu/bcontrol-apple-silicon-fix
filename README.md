# B-Control Apple Silicon Fix (BCR2000 / BCF2000)

Behringer's BCR2000 and BCF2000 only half-work over USB on Apple silicon Macs: MIDI comes out of the device, but nothing gets back in. This is a small firmware patch that fixes it. No kernel extension, no driver, no lowered macOS security settings. Patch the firmware once and USB works in both directions again.

| Model   | Firmware | Status                                                                  |
| ------- | -------- | ----------------------------------------------------------------------- |
| BCR2000 | 1.10     | Tested on a real device, works                                          |
| BCF2000 | 1.10     | **Not tested on a real device yet.** Analysed and patched the same way  |

> **About this repo:** everything here was generated by Claude Code. That includes the firmware analysis, the patch script and this README. Since this is about flashing firmware onto real hardware, that seems worth saying up front. Read the script, check the hashes, and keep the original firmware file somewhere safe.

## What's going on

On M1 and later Macs, a BCR2000 or BCF2000 connected by USB can send MIDI to the computer but can't receive any. Editors never get a reply, presets can't be uploaded, and the LED rings and motor faders ignore incoming MIDI. The same unit works fine on an Intel Mac, or through a DIN MIDI interface on any Mac.

The cause is a mistake in the device's USB descriptor. The bulk OUT endpoint (`0x02`) claims a `wMaxPacketSize` of 4, but USB 2.0 §5.8.3 only allows 8, 16, 32 or 64 for full-speed bulk endpoints. Apple silicon's USB controller is strict about this and refuses to set the endpoint up. With a BCR2000, the kernel log shows:

```text
IOUSBHostFamily::validateEndpointMaxPacketSize: USB 2.0 5.[5-8].3: endpoint 0x02 invalid wMaxPacketSize 0x0004
AppleUSBXHCICommandRing::addEndpoint: completed with result code 17
```

Intel Macs and Linux let the bad value slide or quietly correct it, which is why the bug only shows up on Apple silicon.

## How the fix works

The bad number in the descriptor is the whole problem. The firmware already sets the USB hardware up for 64-byte packets on that endpoint, and its receive code already handles several MIDI events per packet. So the patch just changes the advertised value from 4 to 8 in the four descriptor sets used by USB modes U-1 to U-4. Nothing else changes, and the device still reports firmware 1.10.

The BCF2000 has exactly the same bug. Its USB descriptor block is byte-for-byte identical to the BCR2000's (even the product ID, `0x00BC`). Its code sets the same 64-byte hardware limit and has the same multi-event receive loop. Only the location in the image is different. So the BCF2000 patch is the same 4 → 8 change, but **nobody has tried it on a real BCF2000 yet**. Reports from anyone who does, good or bad, are very welcome as an issue.

`patch_bc2000_usb.py` double-checks itself at every step:

- it only accepts the official BCR2000 or BCF2000 firmware 1.10 files, verified by SHA-256;
- before patching, it re-encodes the untouched firmware and checks the result is byte-identical to the original;
- after patching, it decodes its own output from scratch and checks that exactly four bytes changed;
- it checks the output against a known SHA-256.

Behringer's firmware isn't included here. It's available from Behringer (link below).

## Requirements

- A BCR2000 or BCF2000 and the official firmware 1.10 file for it. Behringer ships both in one archive: [bcf2000_1-10.zip](https://cdn-media.empowertribe.com/67d19225f7884456b2ba3274c20cc602/bcf2000_1-10.zip).

  | File               | SHA-256                                                            |

  | `bcr2000_1-10.syx` | `9ebef1c75aa07d00613a20fb8cd9d58dbcfa9f076f1d8657904e3a6a669bae1d` |
  | `bcf2000_1-10.syx` | `9c9a79cf54e0bcee6827db2c77f491663b4fdb9cd25006207c476418c67a98d3` |

- Python 3. On macOS, if `python3` is missing, `xcode-select --install` takes care of it.
- Behringer's BC Manager software (preferred), or another SysEx sender such as [SysEx Librarian](https://www.snoize.com/sysexlibrarian/) on macOS.
- A way to get the file onto the device, either:
  - **USB from a computer where sending to the device already works** (an Intel Mac, Windows or Linux), or
  - **a DIN MIDI interface** wired to the device's MIDI IN and OUT. This works from any computer, Apple silicon Macs included.

The catch: the fix can't be flashed over USB from an Apple silicon Mac, because USB output to an unpatched device is exactly what's broken.

## 1. Build the patched firmware

Run the script on the file for the right model:

```sh
python3 patch_bc2000_usb.py bcr2000_1-10.syx   # BCR2000
python3 patch_bc2000_usb.py bcf2000_1-10.syx   # BCF2000
```

Expected output:

```text

Patched 4 USB descriptors (bulk OUT wMaxPacketSize 4 -> 8).
Wrote bcr2000_1-10-usbfix.syx
sha256 3402425ca2f8d6d0934c50aa30a66e7d1ae909b66abd09d2f502a91b64437f8c
```

If the script prints an error, stop there and don't send anything to the device.

## 2. Flash it

The file has to match the model: BCR2000 firmware for a BCR2000, BCF2000 firmware for a BCF2000.

The preferred way to flash is with Behringer's **BC Manager** software, with the device connected over **DIN MIDI** and set to **S-4 mode**. That way it doesn't matter whether USB output works, and the setup is the same one used for recovery if anything goes wrong.

1. Keep the original `.syx` file somewhere safe. It's the way back.
2. Connect the device's MIDI IN and MIDI OUT to a MIDI interface with two DIN cables (device OUT to interface IN, interface OUT to device IN).
3. Set the device to S-4 mode:
   1. Hold **EDIT** and press **STORE**. The global setup menu opens.
   2. Turn push encoder 1 until the display shows `S-4`.
   3. Press **EXIT**. Global setup changes are saved automatically.
4. Open BC Manager, select the MIDI interface's ports as input and output, and check that the device is detected.
5. Use BC Manager's firmware update function to send the `-usbfix.syx` file.
6. Wait for the transfer to finish, then power-cycle the device.

Any other SysEx tool, or a USB connection from a computer where USB output works, can do the job too: send the `-usbfix.syx` file the same way as an official Behringer update. If the transfer fails or stalls, increase the delay between messages and try again.

## 3. Try it on the Apple silicon Mac

S-4 is a standalone mode, so switch the device back to a USB mode first: same global setup menu (**EDIT** + **STORE**, push encoder 1), pick one of `U-1` to `U-4`, then **EXIT**.

Plug the device in by USB and send it a request from an editor (for example [BCEditor](https://bceditor.com)). It should answer, and the LED rings or motor faders should follow incoming MIDI.

The endpoint rejection should also be gone from the kernel log:

```sh
log show --last 5m --info --debug --predicate 'eventMessage CONTAINS "validateEndpointMaxPacketSize"'
```

## If something goes wrong

No need to panic. Firmware updates only write the operating-system area of flash and never touch the bootloader, so the bootloader's rescue mode is always there:

1. Switch the device off and wait a few seconds.
2. Hold **STORE** and **LEARN** while switching it back on. The display shows `load`.
3. Send the original `.syx` for the model through the **DIN MIDI IN** port. Rescue mode doesn't work over USB.

To undo the patch on a working device, just flash the original `.syx` the normal way.

That approach requires lowering macOS security (`csrutil enable --without kext`); this firmware patch doesn't.
- [TheKikGen/BCR2000-dev](https://github.com/TheKikGen/BCR2000-dev) is the unofficial B-Control development kit, originally by Willem van Engen ([willem.engen.nl/projects/bc2000-dev](https://willem.engen.nl/projects/bc2000-dev/)). It documents the firmware container format, the OS image cipher and checksums, the memory map, the bootloader rescue mode and the ML671000 CPU. The encoder and decoder in `patch_bc2000_usb.py` are a Python 3 port of its `bcfwconvert.py`, with one fix: firmware page addresses are decoded as 16-bit values, because the original reads them wrongly above 64 KB.
- The OKI ML671000 User's Manual (included in BCR2000-dev) documents the USB controller registers. Both firmwares write 64 to `EP2PLD`, which shows the hardware already accepts 64-byte packets on endpoint 2.
